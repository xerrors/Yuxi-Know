# 设置界面共享样式归属

状态：implemented
类型：simplification
Owner：frontend/src/assets/css/settings.less

## 问题

设置弹窗通过高优先级后代选择器覆盖面板的标题与说明，导致 OCR 的说明间距、字号和行高与局部声明不符。账户面板依赖弹窗提供页头样式，用户、部门与 API Key 面板分别复制页头和表格外观，同类设置存在缺乏业务用途的差异。

## 决策

### 实现方案

全局样式入口一次引入设置样式，公共类使用明确的 `settings-` 前缀，由组件主动使用。共享样式拥有分区标题、说明、页头操作、表单行、服务卡片和管理表格。设置弹窗只拥有导航、内容区和浮层布局，不再接管任意后代的通用类。

分区间距使用 `settings-section-block`，普通卡片使用 `settings-surface-card`；定时任务和 Skill 详情中已有的 `settings-section`、`settings-card` 继续属于原组件，不能因类名相似被全局规则接管。[设置表单共享样式](./2026-10-18-settings-form-style.md)中的布局决定继续适用，表单与服务卡片样式由本入口统一装配。

同类说明采用 12px、次级文本色和 1.6 行高，标题与分区间距统一。保留模型选择器、普通选择器与数字输入的真实宽度差异，以及服务卡片的编辑、键盘访问和窄容器布局。账户资料、沙盒状态、用户筛选和表格业务列仍由各组件拥有。刷新按钮和动画复用已有管理控件样式，不增加组件框架、依赖或配置。

## 替代方案

- 保留 scoped LESS 并只提取说明：不能消除弹窗优先级冲突和管理表格的重复 Owner。
- 为每类分区封装 Vue 组件：当前共享需求以外观为主，额外 props 和 slot 增加维护负担。
- 全站统一所有同名类：不同模块存在用途不同的标题和卡片，扩大影响范围。

## 后果

公共外观的修改同时影响所有主动使用对应类的组件。组件独立挂载时需要与应用一样加载生产样式入口；不能依赖设置弹窗提供隐式皮肤。窄布局依据组件容器宽度，不依据视口宽度；紧凑控件在纵向排列时明确重置 flex，避免横向尺寸变成纵向留白。

## 验证

`frontend/test/browser/settingsStyles.html` 装配真实生产组件、主题和完整样式入口，配套脚本读取 DOM、computed style 与布局边界。浅深主题各覆盖八个设置菜单及 1440、1024、768px 视口，并检查四个独立面板、500px 表单与服务容器、480px 页头、三个管理面板的 loading、empty、error。定时任务与 Skill 详情使用真实组件证明旧类未受污染；模型供应商列表和 Debug 基础控件完成浅深色检查。注入旧弹窗说明覆盖规则或恢复紧凑控件的纵向 260px flex basis 时，对应断言明确失败，清理后通过。样式脚本的 HTTP 响应均由浏览器内固定数据提供，业务写入请求为零。

网络搜索浏览器回归覆盖编辑、取消、保存、测试失败与恢复，所有请求均被拦截。前端 `lint:check`、全量 unit（809 项）、生产 build、工程契约检查及其 66 项单测通过。验证使用挂载当前工作区的 `yuxi-container-e2e-frontend-1` 容器执行 `docker exec … pnpm run …`。真实供应商请求与完整登录链路未验证；本决定不改变这两处业务边界。

旧能力不存在：两个 scoped LESS 文件、面板内重复的公共页头与表格皮肤、弹窗针对通用标题和说明类的后代覆盖均已删除；没有保留旧类名作为兼容别名。

重新引入条件：存在当前共享样式无法表达、且有实际使用者的业务布局时，再添加由对应组件拥有的局部差异。
