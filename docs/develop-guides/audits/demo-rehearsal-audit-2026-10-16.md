# 售前演示排练与能力排查

面向 Yuxi 维护者与演示视频制作者，记录真实客户提案任务中的能力、交付质量和录制条件。排练日期为 2026-10-16，使用当前工作树对应的 Docker Compose 服务与真实模型；客户、产品、报价和验收指标全部为虚构演示资料。

## 验证范围与演示资料

演示主线为“明天向客户提案，先依据内部资料与公开参考交付方案网页，再制作可编辑 PPT，最后响应预算与周期变化”。观察边界包括知识库文档最终状态、工具调用结果、子会话与 Turn 状态、生成文件字节、网页交互 DOM 和 PPT 渲染。模型的完成自述与 HTTP 成功响应单独不构成通过。

本次排练保留现有业务代码与运行服务，仅创建演示知识库、私有智能体、项目、会话和产物。案例中的 ERP、语音、报价与验收目标用于检验方案推导，不表示 Yuxi 已提供对应业务集成或达到案例指标。

资料包括三份入库 Markdown 和一份项目文件：现行产品报价、现行交付范围、已过期的历史案例、客户会议纪要。当前报价从 2026-10-01 生效；历史案例中的免费 ERP 属于过期个案。会议纪要的初始需求为 30 名客服、2000 份文档、预算上限 20 万元、8 周内交付完整方案；修订需求将预算与周期改为 8 万元和 4 周。

金额单位均为万元，且包含导入与培训服务。独立验算结果为：

| 配置 | 金额计算 | 合计 | 周期 | 初始需求 | 8 万元和 4 周限制 |
| --- | --- | --- | --- | --- | --- |
| 基础试点 | 4.8 + 1.2 + 0.8 | 6.8 | 4 周 | 预算和周期满足，缺少所需扩展 | 满足 |
| 基础试点与 ERP | 6.8 + 2.4 | 9.2 | 6 周 | 预算和周期满足，缺少语音 | 不满足 |
| 基础试点与语音 | 6.8 + 3.2 | 10.0 | 6 周 | 预算和周期满足，缺少 ERP | 不满足 |
| 完整方案 | 6.8 + 2.4 + 3.2 | 12.4 | 8 周 | 满足，排期没有缓冲 | 不满足 |

四周基础试点依次完成资料清理、入库配置、客服试用、验收培训；ERP 和语音各增加两周，按资料要求串行叠加。100 个售后问题中至少 85 个回答有依据且正确属于后续试点的验收目标，排练不执行该业务效果测试。

协作与执行语义以[会话协作](../../agents/session-cooperation.md)和[沙盒机制](../../mechanisms/sandbox.md)为准；文件与 Skill 的安装、发现和激活方式见[Skills 管理](../../agents/skills-management.md)。

## 首轮执行与环境问题

首轮使用 GLM 5.3 Flash 自由编排。主会话创建内部核验与公开调研两个子会话，调研成员继续创建 Dify 和 MaxKB 两个成员，整树共五个会话。内部核验交付文件；公开调研持续补搜商业许可与其他细节，约十四分钟后仍未交付主方案和网页，操作者停止整树。停止后回读所有成员，确认已无活动 Turn，已有核验文件保留。本轮记录为未完成。

操作者曾向两个运行中的调研成员提交收束范围的 steer。回读 Input 确认两条输入均已消费，沿用原 Turn 并创建后续 Run；这证明接收与执行归属，不证明成员已经完成新的交付要求。整树停止前未拿到两份最终简报。

| 观察项 | 实测结果 | 对录制与产品的影响 |
| --- | --- | --- |
| 模型可用性 | 一个已配置模型返回 429 额度耗尽，另一个返回 402 余额不足 | 录制前需验证实际模型调用；readiness 不覆盖供应商额度 |
| 临时账号 | 初次使用的临时测试账号在排练期间失效，后续改用稳定用户的独立演示项目 | 属于环境干扰，不归因为会话协作缺陷 |
| 知识库 | 三份 Markdown 完成上传、解析与向量入库；Agent 检索并打开原文 | 知识库链路可用于此案例 |
| 核验内容 | 价格、组合合计与周期正确；报告额外写入“ERP 先于语音延后”，并把只读误解为不能读取实时库存 | 引用和核验角色不能代替逐句核对；仅把明确来源的约束传给制作角色 |
| 调研范围 | 一项公开参考任务扩展为多层调研与持续补搜 | 演示任务需要明确检索范围和停止条件；本次未做严格的模型性能对比 |
| 域名约束 | `web_search` 指定 `sites=["github.com"]` 时，实际返回包含 `pkg.go.dev`、`blog.hotgithub.com` 的结果 | 不能将请求参数视为严格结果过滤；最终引用需要核验 URL |
| 运行依赖 | 用户安装个人 `pptx-generator` Skill，但当前 VM 全局包与 Skill 目录未找到 PptxGenJS，`markitdown`、`soffice` 和 `libreoffice` 命令不可用 | 安装 Skill 与准备运行依赖是独立事项 |
| 基础执行环境 | 实际命令确认 Python、Node、Python Playwright、Chromium 安装目录与 Noto CJK 字体可用 | 可以继续验证脚本生成、网页和中文渲染 |

依赖判断来自实际 `execute` 结果与生成的环境检查 JSON 回读。浏览器安装目录存在不等于浏览器启动成功，后续仍需真实页面验证。API 镜像配置包含 LibreOffice，Office 预览用例也已接入转换器；用户 VM 中缺少转换程序不等于产品没有 PPT 预览，最终仍以成品预览为验收。相关 Owner 为 [API 镜像](https://github.com/xerrors/Yuxi/blob/main/docker/api.Dockerfile)、[用户 VM 模板](https://github.com/xerrors/Yuxi/blob/main/docker/cube/Dockerfile.user)及[产物预览用例](https://github.com/xerrors/Yuxi/blob/main/backend/yuxi/modules/agents/services/artifacts.py)。

## 精简复跑的报告与网页

精简复跑使用 DeepSeek V4 Flash，最多两个直接子会话、全树最多两次公开搜索，要求未确认的信息保留状态。复跑复用第一轮的内部核验文件，并由操作者明确指出其中的两项语义误读。模型、提示范围与既有材料同时变化，不能将耗时差异单独归因于某个模型。此前独立短探针实际执行 `python3 -c "print(1+1)"` 并得到 `2`，对应 Turn 约六秒完成，仅证明该模型与沙盒短链路可用。

主会话分出报告与公开参考两个成员，自己生成网页，再整合报告。主 Turn 约 227 秒后完成，生成的 Markdown 报告约 16 KB，HTML 约 11 KB。回读工具调用确认实际执行三次搜索，超过要求的两次：一次返回包含石墨文档官网与官方博客的八条结果，两次返回当日配额耗尽错误。成员及主会话都自报仅执行两次，这一自报不准确。报告保留语雀资料“未确认”，本轮没有完成“两家均获得官方资料”的完整目标，文件生成、调用次数与外部资料完整性分别判断。

两次配额失败的原始结果均包含 `error`，公开 `function_call_output` 却为 `status=completed`、`error=null`。工具结果归一化仅将字典中的 `status="error"` 识别为失败，而搜索工具返回的是 `error` 字段；该装配差异需要在搜索结果契约处修正。真实零结果、额度失败和网络失败应可区分，不能以工具调用“完成”表示检索成功。Owner 为[搜索工具](https://github.com/xerrors/Yuxi/blob/main/backend/yuxi/modules/extensions/tools/builtin/web_search.py)与[工具结果归一化](https://github.com/xerrors/Yuxi/blob/main/backend/yuxi/modules/agents/tool_results.py)。

在真实调研成员页面展开失败的搜索调用，DOM 显示“未找到相关搜索结果”，没有显示配额错误。这与协议观察一致。搜索结果展示 Owner 为[搜索工具渲染器](https://github.com/xerrors/Yuxi/blob/main/frontend/src/modules/session/ui/tools/renderers/WebSearchTool.vue)；错误修复需要同时覆盖持久工具结果、公开协议与真实页面。

浏览器从真实会话的文件面板打开生成 HTML，操作实际 iframe DOM，没有替换接口响应或手工修改生成网页。四组金额和周期均与独立验算吻合，但三个负向场景暴露了业务判断问题：

| 场景 | 预期结果 | 实际结果 | 结论 |
| --- | --- | --- | --- |
| 切换 ERP 与语音的四种组合 | 6.8 / 9.2 / 10.0 / 12.4 万元，对应 4 / 6 / 6 / 8 周 | 四组 DOM 数值全部一致 | 算术通过 |
| 初始客户仍要求 ERP 和语音，取消两项 | 明确缺少原定需求，提示这是需要客户确认的缩范围备选 | 显示“满足全部客户约束” | 需求完整性判定失败 |
| 取消培训与验收 | 不能视为完整交付，或固定基础三项不可取消 | 仍显示“满足全部客户约束” | 必需服务判断失败 |
| 完整方案的周期上限改为 10 周 | 8 周交付，剩余 2 周缓冲 | 徽章显示 2 周余量，旁边仍写“零缓冲” | 动态文案不一致 |
| 在网页中点击知识依据 | 能定位依据，或有明确的外部来源入口 | 页面只有文件编号文字，DOM 中链接数为 0 | 该网页未实现来源跳转 |

报告在纠正后没有继续沿用“ERP 先于语音延后”的说法，但对“只读连接器”仍写出了库存读取范围的确定性承诺。资料仅明确未购买时不能承诺相关能力，购买后具体可读字段与实时性仍需确认。后续修订需明确这个边界，不能从条件限制反推完整功能保证。

网页计算和主会话完成状态分别由生成文件与公开协议拥有；“满足全部需求”的业务判断属于生成程序。以上三个问题首先需要修正生成成果与制作方法，不能据此推断 Yuxi 的沙盒或文件预览本身缺失。默认数据检查、JavaScript 语法检查及模型自述均没有发现这些负向场景。

## PPT 生成与渲染结果

单独的 PPT 轮次约 172 秒完成。Agent 在项目内执行 `npm install pptxgenjs --no-audit --no-fund`，约三秒安装完成，未做全局安装。随后生成八页脚本、编译 PPTX，并解压逐页提取 XML 文本完成内容核对。`markitdown` 缺失没有阻断本次文本检查。Agent 如实说明 VM 缺少 LibreOffice，未做视觉渲染校验。

下载原文件后独立检查 ZIP 完整性与八份 slide XML，确认存在原生文本形状和表格；产品 Office 预览接口返回有效 PDF，独立渲染得到八页。该结果证明可生成含可编辑对象的 PPTX，不代表已经在桌面 PowerPoint 或 WPS 中完成编辑兼容测试。

实际渲染发现第 5 页深色表头的文字不可见，第 8 页来源卡片的两行文字重叠。主要预算 12.4 万元、基础三项 6.8 万元、全量排期 8 周及“85/100 是目标”均保留，但成品需要修正排版后才能录制。文字抽取能读到相关内容，无法发现其渲染后的对比度与重叠问题。

浏览器首次打开 PPT 时，PDF 组件出现加载失败；控制台记录为 Vite 动态依赖返回 `504 Outdated Optimize Dep`。刷新页面后同一文件渲染出八个 PDF canvas。该问题属于本次开发环境的依赖缓存失效，不能据此宣布产品不支持 PPT 预览，也不能把一次刷新恢复推广为生产环境验证。

## 预算变更与同名文件更新

操作者在真实聊天输入框提交预算降至 8 万元、四周仅做知识助手试点的变更，同时指出网页判断问题及 PPT 两处排版问题。要求保留三个文件名并标注修订版。该轮约 347 秒完成，Agent 修改报告、HTML 与 PPT，实际通过用户 VM 中的 `agent-browser` 操作网页，检查选项、预算和周期，并重新编译 PPT。

独立回读三份产物，确认本期推荐均为基础三项 6.8 万元、4 周，预算上限 8 万元，ERP 与语音本期延后。修订后 HTML 的四组组合算术、延期范围提示、基础三项固定勾选、低预算拒绝、短周期拒绝和 10 周上限下的缓冲提示通过真实 iframe DOM 检查。修订 PPT 仍为八页，产品转换器返回有效 PDF；第 5 页表头恢复可读，第 8 页来源卡片不再重叠。封面副标题仍有单字换行，最终录制前需要审片。

同名预览更新存在可复现的问题：保持第一版 HTML 预览打开，经正常聊天界面提交修订，等待 Turn 完成。后端下载已是修订版、默认预算 8、周期 4、合计 6.8，但当前 iframe 仍显示旧版预算 20、周期 8、合计 12.4。点击最新交付卡片仍显示旧内容；关闭该预览标签再打开才读取修订版。录制“临时改需求，现场看成果变化”前需要修复这一问题。Owner 为[会话预览缓存](https://github.com/xerrors/Yuxi/blob/main/frontend/src/modules/session/ui/SessionWorkspace.vue)和[文件面板加载](https://github.com/xerrors/Yuxi/blob/main/frontend/src/modules/session/ui/workspace/AgentPanel.vue)。验收需同时核对文件字节和一直打开的 DOM，重新加载整个页面不能替代此验收。

修订报告及 PPT 第 8 页仍有来源表述问题：新预算与范围来自最新用户确认，原会议纪要仍保存 20 万元、八周完整范围，两份成果却继续将修订需求归于会议纪要。报告的公开调研部分也保留了错误的“两次调用”表述。对金额和范围的修改成功，不代表整份文档已经完成语义审阅；剩余问题应在正式录制资料中纠正。

本次同名修改后，历史交付路径读取当前 Workspace 文件；原件对照依赖预先保存的副本。录制使用不同版本文件名可以保留对照，完整历史快照属于需要另行决定的产品能力。

## 录制前的修复与能力补齐

知识库、协作、沙箱执行、网页生成、PPTX 生成、Office 预览和多轮修改都有真实结果。当前主要缺口集中在失败表达、成果验收和更新体验。建议按下表处理，已有能力通过配置与 Skill 使用，平台缺陷在实际 Owner 修复。

| 优先级与类别 | 建议 | 最小验收 |
| --- | --- | --- |
| P1 平台缺陷 | 搜索失败在工具结果、公开协议和页面中保持错误语义，区分零结果、配额耗尽与网络失败 | 注入配额失败，公开输出带错误，真实 DOM 显示失败原因，不能显示为零结果 |
| P1 平台缺陷 | 同名产物被 Agent 修改后使预览缓存失效，最新卡片读取最新内容 | 保持旧预览打开，经聊天更新文件；文件字节与当前 DOM 都显示新预算，点击新卡片也不复用旧内容 |
| P1 检索契约 | 对最终搜索结果核验请求中的域名范围 | 使用包含站外 URL 的供应商响应，不能把站外结果作为限定站点结果交付；过滤后为空要明确说明 |
| P1 交付方法 | 在演示 Agent 的专属 Skill 中固定资料优先级、范围与金额核验、负向交互检查、未确认来源和停止条件 | 恢复本次错误，缺少必需项、错误缓冲、条件推断和调用次数误报必须被发现；成品检查读取实际文件与 DOM |
| P2 运行准备 | 给常用制作 Skill 提供依赖检查，针对 PPT 与浏览器先核对真实导入和命令执行 | “Skill 已安装”与“依赖就绪”分开显示；缺失依赖能定位，并能在项目内安装后重新检查 |
| P2 模型可见的渲染 | 复用现有 Office 转换器输出逐页预览，供支持视觉的模型或人工检查 | 第 5 页低对比度表头与第 8 页文字重叠能在渲染检查中被发现；访问仍经过产物授权边界 |
| P2 来源与版本体验 | 为交付物补来源清单与修订说明，录制先用不同版本文件名保留对照 | 用户能打开原始依据，并分清当前版、上一版及变更；聊天已有来源能力不等于生成 HTML 自带来源跳转 |

模型设置页已有真实的“测试模型连接”入口，不需要另建一套模型管理机制。录制前复用该入口并做一次带工具的短探针；本次普通模型连接状态不能替代复杂任务成功率。公开搜索的提示次数上限没有阻止第三次调用，若产品需要严格成本限制，应在执行边界形成约束；当前录制流程先控制题目范围并核对真实调用记录。

三类成果可先共用当前项目内的一份报价与范围数据文件，再从这份数据生成报告、网页和 PPT，减少多处独立改写。该文件是本次客户方案的生成输入，仍需保存来源与最新用户确认；不建立仓库级主张台账或复杂的成果依赖框架。

## 主片与短片剧本

主片主题为“预算只剩八万，Yuxi 如何修改一份能交付的方案”，剪辑目标约五到六分钟。观众依次看到内部资料影响决策、实际协作、可使用成果，以及用户改变条件后的修改。等待阶段允许加速，并标出实际耗时；当前实测的约 227 秒、172 秒、347 秒分别属于报告与网页、PPT、反馈修订三个轮次，不能宣称一次输入即时交付。

| 剪辑段落 | 用户操作与镜头 | 需要证明的事实 |

## 后续场景的选择

以下场景是下一轮候选，本轮未实跑，不计入已验证能力。优先选择能产生可操作成果、存在可核验约束、允许现场变更的任务；每条视频只保留一个主要冲突。

| 场景与开场 | 可以拍到的动作与成果 | 现场变更 | 下一轮重点排查 |
| --- | --- | --- | --- |
| 经营诊断：“销售额上涨，为什么利润下降？” | 上传虚构订单与成本表，结合内部定价规则；分工核算与解释，沙盒计算，交付可筛选看板和经营汇报 | 排除一笔退款，或切换毛利口径，观察图表与结论是否同时变化 | 表格解析、真实计算结果、口径溯源和多成果一致性；不预设已接入企业数据库 |
| 产品发布：“下周发布，但只能做三个功能” | 从访谈与反馈中归纳需求，分工核对证据与竞争参考，交付可点击原型、范围清单和发布演示稿 | 删除一项关键功能，现场调整原型与发布承诺 | 需求与界面是否对应，原型交互是否真实，是否把原型误称为已上线产品 |
| 新人培训：“把厚手册变成能练习的上岗课程” | 读取制度和操作手册，分工设计知识点与情境题，在沙盒生成练习网站和讲师课件 | 更新一条政策，观察课程、答案与解释是否同步 | 新旧规则冲突、评分逻辑、引用依据；不将生成题目等同于培训效果达标 |

建议先录已经排练的客户提案，再排练经营诊断。前者突出内部知识、协作与修改，后者补充真实数据计算的说服力。产品发布适合视觉传播，培训适合面向企业采购者解释知识库价值；两者都应在实跑后决定是否纳入正式宣传。
