# 演示交付修复与复跑

本文面向 Yuxi 维护者与演示制作者，记录 2026-10-18 对[首轮排练](./demo-rehearsal-audit-2026-10-16.md)中两项缺陷的修复与真实流程复跑。客户、产品、报价与验收指标均为虚构资料。目标是证明搜索失败与零结果可区分、同名产物修改后预览更新，再检查知识库、协作调研、网页、PPT 和需求变更的实际结果；其它解析模块的并行改动不属于本次交付范围。

## 两项修复的边界

当前搜索服务已经将供应商错误转换成领域异常，注册工具将其转换为错误 ToolMessage。新增回归通过真实注册工具验证 Tavily、DeepSeek、豆包三种配置下的额度失败，并经工具结果契约核对公开错误正文；正常零结果保留成功。前端补齐历史搜索仅含非空顶层字符串 `error`、外层仍标记完成的展示，搜索卡片和调用汇总均按失败处理。兼容仅限已有网页搜索工具，保留数据库历史内容。

预览终态通知使当前线程缓存失效，不依赖文件面板是否打开、是否正在查看产物、页面是否在浏览器后台。活动产物重新读取；关闭后重开、从协作或个人文件标签切回时读取失效后的内容。缺少文件元数据的交付卡片重复打开时重新读取。既有 Workdir 元数据轮询继续负责运行期刷新，后台标记已读和自动滚动的条件保持原样。

真实组件测试还覆盖 reactive Map 对文件对象的包装：多个预览请求共享读取时，等待方按原始响应对象确认缓存归属，失效前的旧请求不能覆盖新缓存。实现复用既有线程终态通知与文件接口，不新增文件版本协议、历史快照或供应商回退。当前机制见[文件边界与预览](../../mechanisms/sandbox.md#文件边界)及[网络搜索与正文工具](../../agents/tools-system.md)。

## 负向与页面验证

先补用例再改实现，初始实际复现三个旧预览失败和一个历史搜索状态失败；独立审查又复现关闭面板及切到协作标签期间的缓存遗漏。相关断言均读取真实组件状态或渲染结果，失败时直接显示旧“预算20万元”，不是只检查刷新函数调用次数。

上次保存的两条额度失败记录在真实会话页面重新展开后，均显示失败图标、失败汇总和原始错误详情，没有“未找到相关搜索结果”。另保留成功搜索的正常状态。页面截图覆盖浅色、深色及 1440、1024、768 像素宽度；截图是历史内容重新展示的证据，不冒充本轮真实供应商再次触发配额失败。

另外创建独立验证会话，由真实模型调用一次 `web_search`，实际参数为 180 个英文 `q`。当前 DeepSeek 搜索在供应商调用前拒绝超长查询；公开持久结果为 `status=failed`，错误正文为“搜索词超过当前供应商的长度限制”，真实页面显示同一失败原因，没有零结果文案。该探针证明 API、worker、工具、持久结果与页面的失败链路；配额失败本身由注册工具的确定性 HTTP 回归与历史页面共同覆盖，两种证据分别记录。

## 真实提案复跑

复跑重新上传、解析和入库三份虚构资料，并上传原始客户会议纪要。三份知识文档最终均为 `indexed`。新建私有演示 Agent 使用当前目录中可用且连接测试通过的 `deepseek:deepseek-flash`；上次使用的模型标识已不在当前目录，本次没有恢复旧配置或修改全局默认供应商。

第一轮要求最多两个直接子会话、全树最多两次搜索，先交付报告与离线交互网页。实际创建内部核验和公开参考两个成员，没有进一步拆分；回读全树公开工具记录确认两次 `web_search`、四次 `web_fetch` 均完成，搜索词不含客户名与内部报价。两家厂商均取得官方页面，部分业务问题仍明确保留“未确认”，不把没有找到某项说明推断为厂商不支持。主 Turn 约 382 秒完成，交付报告、HTML 与共用方案数据。

独立操作产品 iframe 中的真实控件，四组金额为 6.8、9.2、10.0、12.4 万元，周期为 4、6、6、8 周。缺少 ERP 或语音会提示原客户需求未覆盖；预算降至 10 万元或周期缩至四周时，完整方案分别提示超预算与超期。网页提供三条官方参考链接，内部依据展示原句与文档标识。

第二轮制作八页 PPT，约 358 秒完成，最终交付原件为 293070 字节；ZIP、八份 slide XML 与原生文本对象检查通过。产品转换器返回有效八页 PDF，逐页实际渲染可读，上次的深色表头不可读和来源卡片重叠没有重现。Agent 因 VM 缺少 Office 渲染程序，另写并反复调整简化 XML 渲染器；操作者提交一次收束 steer，回读 Input 确认在同一 Turn 消费，最终交付才结束。因此该轮不能当作完全无干预的稳定演示，也不能把简化渲染结果当成真实 Office 渲染。

期间共享 API 与 worker 被重建，服务恢复后 API 已返回会话完成，旧页面仍显示“正在生成回复”且没有 PPT 卡片。截图与同一时刻的 API/DOM 对照保留此现象，尚未隔离其恢复根因。刷新后读取到最终历史。PPT 页面又出现 Vite 的 `504 Outdated Optimize Dep`，普通刷新未恢复；重启前端开发服务后，真实页面渲染出八个 PDF canvas。服务重建后的聊天流恢复与开发依赖缓存分别记录，不能归因为 PPT 文件无效，也不能宣称本轮全程没有人工恢复。

## 继续对话与静默连接修复

需求变更轮次只更新了共用 JSON，报告、HTML、PPT 的 SHA-256 与原版相同，但 Turn 显示 completed。继续同一对话时供应商返回工具结果缺少配对调用的 400。直接读取 PostgreSQL checkpoint 后确认：最后一次 `write_file` 参数无法解析，AI 的合法调用为空、`invalid_tool_calls` 非空；这导致图正常结束。下一次输入的 PatchToolCallsMiddleware 补入失败 ToolMessage，已有发送净化删掉畸形调用却保留结果，才产生不配对请求。该因果由 checkpoint 与发送载荷证明，不能归因于同期服务重建。

结算服务现在拒绝用最终畸形调用完成 Run，沿既有失败通道记录中文原因，不猜测参数并执行。Chat Completions 发送边界保留失败文本，仅过滤同批已移除调用对应的补齐结果；合法工具结果、跨用户/系统消息边界的真实孤儿和原始 checkpoint 保留。确定性 E2E 经实际 HTTP、worker 和 PostgreSQL 验证第一轮失败、同一会话第二轮成功，并回读原 checkpoint 确认错误证据仍在；回归接入现有确定性 E2E 选择器。

前端读流在连续 60 秒没有任何字节时关闭失效 reader，进入既有 Turn 对账和 cursor 重连。默认 15 秒心跳保持正常长任务订阅，超时不取消任务。负向用例在旧实现下继续显示 in_progress；修复后回读 completed、加载最终历史并发出产物刷新通知。额外覆盖持续心跳、运行态按原游标重连及停止订阅后不再重连。

原失败会话的真实模型继续轮次约 8.2 秒完成，只读取一次现有 JSON 并正确报告 v2.0、预算 8 万元、四周，同时指出其它三个交付物仍为旧版。页面验证只注入一次无字节 GET SSE 响应，约 60 秒后取消失效 reader、回读同一 Turn 并显示该最终回答；performance.timeOrigin 未改变，期间没有页面刷新。故障注入针对传输，模型、工具、文件与 PostgreSQL 均为真实链路。它证明静默读流恢复路径，不冒充服务重建的所有可能故障均已验证。

## 需求变更与最终产物

恢复后在原会话继续完成预算变更，约 310 秒结束；报告、HTML、JSON 和八页 PPT 均按原名更新。期间在确认没有其它活动 Run 后受控重启 API，worker 保持执行，服务 readiness 恢复后页面自动重连；同一页面收到 completed 并读取新产物。该验证覆盖 API 进程重启，未重启活动 worker，也不代表所有容器重建时点均被覆盖。

变更前预览保持打开，内容为 20 万元预算、八周上限、12.4 万元完整方案。终态后无需整页刷新，真实 iframe 展示 8 万元预算、四周上限、6.8 万元基础方案；performance.timeOrigin 始终相同。再点击最新同名 HTML 交付卡片，内容仍为新版本。实际 iframe DOM 的四组组合为 6.8/9.2/10.0/12.4 万元和 4/6/6/8 周；追加任一延期项均明确超出 8 万元与四周，基础方案把周期上限改为六周时显示两周缓冲。明细合计说明随组合改变，保留三条官方链接。

最终文件回读确认新需求归属 `需求变更-20261018.md`，原会议纪要仍保留初始需求。计费周期统一标为未载明，验收指标保留目标与未实测状态。四份文件的 SHA-256 均改变，逐份下载上一版副本后与基线字节一致；原会议纪要字节不变。

真实 Office 渲染发现变更版封面副标题与大标题重叠、底部说明有孤字换行。操作者给出一次具体版式反馈，Agent 只调整封面并重新生成；独立比较 slide XML 确认第 2–8 页不变。最终 PPT 为 306448 字节，含八页原生文本对象，产品转换得到八页 PDF并实际渲染；产品页面同一页面显示八个 PDF canvas。封面修正后的来源、预算、周期与验收标签均可读。真实渲染和文字结构检查分别记录，不能把后者替代前者。

本轮包含 PPT 收束 steer、运行恢复验证、明确交付补全要求和封面版式反馈，不能宣传为完全无人干预的一次生成。录制主线仍可用“内部依据与过期案例 → 两个成员协作核查 → 可交互网页 → 八页 PPT → 预算变更 → 具体反馈修订”；加速等待时标注实际耗时。剧本分镜见[排练剧本](./demo-rehearsal-audit-2026-10-16.md#主片与短片剧本)，执行能力与录制条件以本文复跑结果为准。

## 剩余问题与录制边界

当前没有观察到上述已修缺陷再次出现。仍需补齐的能力首先是让 Agent 在制作阶段直接使用受授权的真实 Office 逐页渲染结果；当前用户预览可用，VM 中没有 Office 命令，Agent 曾用自写近似渲染替代。把已有转换能力接到模型可用工具，比要求模型自行实现渲染器更符合这条交付链路，仍需另行设计权限与图片预算，本次没有新增该工具。

生成成果仍需要来源和视觉审阅：本轮经反馈纠正未载明的“一次性报价”、动态金额说明、新需求来源与封面换行。未来追加项的先后顺序没有资料依据，当前时间轴只能作为示意，不应讲成既定交付承诺。网页版本标签重复 `v` 也在生成脚本中修正，回读实际 HTML 确认为 `v2.0`。

Agent 完成文件后曾保留七条 pending 待办。独立验收确认后，操作者另行要求更新，实际 `write_todos` 将七条全部标为 completed；没有让平台无条件把未完成事项标为成功。录制 Agent 的交付规范需要声明未验证项、调用产物展示，并对真实文件与 DOM 完成最后检查。严格的检索次数、交付质量和默认无干预稳定性仍不能仅靠自然语言要求来承诺。 当轮使用的待办工具属于历史行为，当前能力见[移除智能体待办中间件](../decisions/implemented/2026-10-18-remove-agent-todos.md)。

文档检查包含本文、两份 implemented decision 与 owning 文档的相对链接检查、`pnpm --dir docs run build` 及 `git diff --check`；文档构建完成，仅有已有 chunk 大小提示。原始截图、新旧产物、文件摘要与验证记录保留在本地演示材料目录；对外素材包仅包含虚构资料、成品、预览与审计，不含认证文件或环境配置。
